# CI and signed releases — design

Status: proposed · Date: 2026-09-28 · Plan: `docs/superpowers/plans/2026-09-28-ci-and-signed-releases.md`

## Problem

Kubepit has no automation. The six checks from `AGENTS.md` run only on the
maintainer's Mac, so Linux and Windows regressions go unnoticed. There is no
way to produce installers: `docs/RELEASING.md` sketches a `tauri-action`
workflow, but nothing signs macOS or Windows builds, nothing produces
`latest.json`, and the in-app updater (`kubepit_core::updates::UpdaterConfig`,
`apps/desktop/src-tauri/src/ipc/updater.rs`) stays inert because no build ever
carries `plugins.updater.pubkey`.

## Goals

1. GitHub Actions run the six checks on every pull request and on `main`, on
   Linux, macOS and Windows runners, with cargo and pnpm caches.
2. Pushing a `vX.Y.Z` tag builds, signs and uploads macOS, Windows and Linux
   bundles to a **draft** GitHub release, together with the updater bundles,
   their `.sig` files, `latest.json` and `SHA256SUMS`.
3. `latest.json` is generated by our own tested script and verified before
   upload. It is compatible with the existing updater, which reads the
   bundled `plugins.updater` config and asks
   `https://github.com/erdembas/kubepit/releases/latest/download/latest.json`.
4. Publishing the release updates a Homebrew cask in our own tap and submits a
   winget manifest update.
5. One documented versioning and changelog convention; one command bumps
   every version file.
6. Everything that can be tested without a real release is tested: `actionlint`
   on workflows, unit tests for every release script, a Rust test that the
   updater plugin parses our feed, and a dry run on a fork.

## Non-goals

- Linux and Windows fixes to the app itself (see
  `2026-09-28-cross-platform-validation-design.md`, which depends on this plan).
- Windows MSI, Windows arm64 and Linux arm64 bundles (open questions).
- Flathub (deferred, reasons below), Snap, apt/yum repositories, the Mac App Store.
- An MSRV (1.89) CI job, nightly builds, auto-merge, release-please.
- Generating or committing any key, certificate or token. Secrets are listed
  by name; the user creates them.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| D1 | Platform-independent checks (`pnpm typecheck`, `pnpm i18n:check`, `pnpm --filter @kubepit/desktop build`, `cargo fmt --all -- --check`, script tests, `actionlint`) run once on `ubuntu-22.04`; `cargo clippy` and `cargo test` run on `ubuntu-22.04`, `macos-14` and `windows-2022`. | Code behind `cfg(windows)` / `cfg(unix)` only compiles on its own OS, so clippy and tests must run everywhere; formatting, catalogs and the TS build do not change per OS. Saves ~2/3 of the runner time for those steps. |
| D2 | The Windows `rust` job starts as `continue-on-error` (`experimental: true`). The cross-platform plan makes it required. | Windows has never been built in CI; blocking every PR on it before the cross-platform work lands would stall development. |
| D3 | CI uses `--locked` for cargo and `--frozen-lockfile` for pnpm. | Lockfiles are committed; CI must build what was reviewed. |
| D4 | Caches: `Swatinem/rust-cache` (key per OS, saved only on `main`) and `actions/setup-node` with `cache: pnpm` (pnpm from the `packageManager` field via `pnpm/action-setup`). | Standard, no custom cache keys to maintain; PRs read `main`'s cache without thrashing it. |
| D5 | Every third-party action is pinned to a full commit SHA with a `# vX.Y.Z` comment; Dependabot (`github-actions`, weekly) proposes updates. A script test enforces the pinning. | The release workflow holds signing secrets; tags are mutable. |
| D6 | The release builds with `pnpm --filter @kubepit/desktop tauri build` directly, not `tauri-action`. Our scripts collect the bundles, give them canonical names, upload them with `gh release upload` and generate `latest.json`. | We own the feed format (D8) and asset names; the same commands run locally; no dependence on `tauri-action`'s changing `v0` behaviour. |
| D7 | macOS ships one **universal** build (`--target universal-apple-darwin`): one DMG, one `Kubepit_<v>_universal.app.tar.gz` served to both `darwin-aarch64` and `darwin-x86_64`. | One artifact to sign, notarize and staple, one cask URL without `arch` branches, users cannot pick the wrong file. Cost: roughly twice the download size. |
| D8 | `latest.json` carries installer-specific keys (`darwin-<arch>-app`, `windows-x86_64-nsis`, `linux-x86_64-appimage`, and `-deb` / `-rpm` only when those bundles have a `.sig`) plus generic `darwin-<arch>` and `windows-x86_64`. It **never** has a generic `linux-x86_64` key. | `tauri-plugin-updater` 2.11 looks up `{os}-{arch}-{bundle}` first, then `{os}-{arch}`. A generic Linux key would hand the AppImage to a `.deb`/`.rpm` install, which then fails `install_deb`'s package check. Without the generic key such installs get `TargetsNotFound`, which the cross-platform plan turns into a clear message. |
| D9 | The updater public key lives in the repository **variable** `TAURI_UPDATER_PUBKEY` and is injected into release builds through a `--config` overlay written by `scripts/release/tauri-config.mjs`. The committed `tauri.conf.json` keeps `pubkey: ""`. `createUpdaterArtifacts` is enabled only in that overlay and only when `TAURI_SIGNING_PRIVATE_KEY` is present. | Local and fork builds stay inert and keep building (RELEASING.md §3: enabling updater artifacts without the private key fails the build). The public key is not secret, so a variable is enough and visible in logs. |
| D10 | Each build job verifies every `.sig` against `TAURI_UPDATER_PUBKEY` (Ed25519/minisign, Node `crypto`, no new dependency) before uploading. | A private/public key mismatch would ship a release that no installed copy can ever install; this is the single most expensive release mistake. |
| D11 | Windows: NSIS installer only (`-setup.exe`, per-user, no UAC). It is the updater artifact and the winget installer. | The updater and winget both work with NSIS; MSI needs numeric-only prerelease identifiers under WiX and doubles signing calls. MSI stays an open question for enterprise deployment. |
| D12 | Linux: `ubuntu-22.04` builds AppImage, `.deb` and `.rpm`. | Building on the oldest supported glibc (2.35) keeps the AppImage runnable on newer distributions; `webkit2gtk-4.1` is available there. |
| D13 | Versioning: SemVer, tags `vX.Y.Z`, 0.x while pre-1.0. A version with a `-` suffix is a GitHub **prerelease** (never served by `releases/latest`). `scripts/release/versions.mjs bump X.Y.Z` rewrites the five version files, promotes the changelog and refreshes `Cargo.lock`; the release fails if the tag and any file disagree. | One command replaces the manual three-file checklist in RELEASING.md; a tag/version mismatch would make the updater offer the same version forever. |
| D14 | Changelog: hand-written `CHANGELOG.md` in Keep a Changelog format. The section of the tagged version becomes the GitHub release body and `latest.json` → `notes` (shown in Settings → About & Updates). **Not** release-please. | Notes are user-facing inside the app and must be curated; the history mixes merge commits and fine-grained fixes. release-please also needs a PAT or GitHub App, because tags created with `GITHUB_TOKEN` do not trigger the tag workflow. |
| D15 | Releases stay **drafts** until the maintainer publishes them; distribution (tap, winget) runs on `release: published`. | Matches the RELEASING checklist; draft asset URLs are not public, so the tap and winget must wait for publication. |
| D16 | Missing secrets never fail a build: signing steps are skipped, the release builds unsigned/ad-hoc and the prepare job prints which signing steps are off. | Forks and dry runs must work; the first release can go out before every certificate exists. |
| D17 | Flathub is deferred. AppImage (self-updating), `.deb` and `.rpm` are the Linux channels. | Inside the Flatpak sandbox the host's `kubectl`, `helm`, exec auth plugins (`aws`, `gke-gcloud-auth-plugin`, `kubelogin`) and the user's shell are invisible. Every spawn would need `flatpak-spawn --host` with `--talk-name=org.freedesktop.Flatpak`, which we cannot apply to exec plugins kube-rs spawns itself, and Flathub builds must disable the in-app updater. |

### Code signing options

**macOS** (required for Gatekeeper and the Homebrew cask): an Apple Developer
Program membership, a *Developer ID Application* certificate (`.p12`) and an
App Store Connect API key for notarization (preferred over an Apple ID with an
app-specific password: it does not expire with password changes and needs no
2FA). Tauri imports the certificate into a temporary keychain, signs with the
hardened runtime, notarizes and staples when `APPLE_CERTIFICATE`,
`APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_API_ISSUER`,
`APPLE_API_KEY` and `APPLE_API_KEY_PATH` are set. Without them the build keeps
the committed ad-hoc identity `"-"`.

**Windows** — options, in recommended order:

| Option | Cost | Automatable in CI | Eligibility / caveats |
|--------|------|-------------------|-----------------------|
| Azure Trusted Signing (Artifact Signing) via `trusted-signing-cli` as Tauri's `bundle.windows.signCommand` | ~US$10 / month | Yes (service principal) | Organizations with verifiable history, individuals only in some countries (check for Türkiye) |
| SignPath Foundation (free for OSS) | Free | Yes, but via their action on uploaded artifacts, not per-file `signCommand` | Project approval; changes the build/upload order |
| OV certificate in a cloud HSM (SSL.com eSigner, Certum SimplySign) | ~US$150–400 / year | eSigner yes (TOTP secret); SimplySign hard (phone app) | Available to individuals internationally |
| Unsigned | Free | — | SmartScreen "unknown publisher" warning; winget still accepts it |

The workflow is provider-agnostic: `scripts/release/tauri-config.mjs` puts a
`signCommand` into the overlay when the repository variable
`WINDOWS_SIGNING_PROVIDER` names a configured provider. This plan implements
`azure`; other providers add one branch to `windowsSignCommand()` and one setup
step. Tauri calls `signCommand` for the app executable and the NSIS installer;
the minisign `.sig` is computed after signing.

## Architecture

```
.github/
├── actions/setup/action.yml      composite: pnpm, Node 22, Rust (+targets), caches, Linux deps, pnpm install
├── workflows/ci.yml              PR + main: frontend, rust-fmt, rust (3 OS), workflows (actionlint)
├── workflows/release.yml         tag / dispatch: prepare → build (3 OS) → finalize
├── workflows/distribute.yml      release published: homebrew tap, winget
└── dependabot.yml                github-actions, weekly
scripts/release/                  Node ≥22 ESM, built-ins only, each with node:test tests
├── versions.mjs                  read / check / bump the five version files
├── changelog.mjs                 extract a version's notes, promote [Unreleased]
├── tauri-config.mjs              release --config overlay from env
├── collect-artifacts.mjs         find bundles → canonical names, sha256, manifest, SHA256SUMS
├── minisign.mjs                  verify .sig files against the updater public key
├── latest-json.mjs               build latest.json from the manifests
├── validate-latest-json.mjs      validate latest.json (also used on fixtures)
├── homebrew-cask.mjs             render Casks/kubepit.rb
└── fixtures/                     latest.valid.json, overlay.example.json (dummy values, no keys)
scripts/ci/test/workflows.test.mjs  invariants over .github/ and docs/RELEASING.md
```

### Release flow

1. `prepare` (Linux): resolve the tag, `versions.mjs check --tag`, extract notes,
   decide which signing steps are available, create the draft release (reuse it
   on re-runs; `--prerelease` for `-` versions).
2. `build` (matrix): macOS universal `app,dmg`; Windows `nsis`; Linux
   `appimage,deb,rpm`. Write the overlay, `tauri build --ci --bundles … --config
   overlay`, collect, verify signatures, upload with `--clobber`, and hand the
   small `manifest-<platform>.json` to `finalize` as a workflow artifact.
3. `finalize` (Linux): build `latest.json`, validate it against the uploaded
   asset names, write `SHA256SUMS`, upload both.
4. The maintainer reviews and publishes. `distribute.yml` then updates the tap
   and submits winget.

With `workflow_dispatch` and `dry_run: true`, no release is created or touched:
everything is uploaded as workflow artifacts.

### Canonical asset names

| Bundle | Name | Updater `.sig` |
|--------|------|----------------|
| DMG | `Kubepit_<v>_universal.dmg` | no |
| macOS update | `Kubepit_<v>_universal.app.tar.gz` | yes |
| NSIS | `Kubepit_<v>_x64-setup.exe` | yes |
| AppImage | `Kubepit_<v>_amd64.AppImage` | yes |
| deb | `Kubepit_<v>_amd64.deb` | if the bundler signs it |
| rpm | `Kubepit-<v>-1.x86_64.rpm` | if the bundler signs it |

## UX

No app UI changes. Users see: signed/notarized installers on GitHub Releases,
`brew install --cask erdembas/tap/kubepit`, `winget install ErdemBas.Kubepit`,
and in-app update offers with the curated changelog section as notes.

## Data / contract changes

- No IPC changes (`types/index.ts`, `lib/ipc.ts` untouched).
- New files only, plus: root `package.json` scripts (`test:scripts`,
  `release:bump`, `release:check`), `CHANGELOG.md`, rewritten
  `docs/RELEASING.md`, a README install section, and two Rust tests in
  `apps/desktop/src-tauri/src/ipc/updater.rs`.
- `latest.json` format: as in RELEASING.md §4, restricted by D8.

## Security and safety

- Top-level `permissions: contents: read`; only `prepare`, `build` and
  `finalize` get `contents: write`. No `pull_request_target`. Secrets are only
  read in `release.yml` / `distribute.yml`, which never run for PRs.
- The Apple API key is written to `$RUNNER_TEMP` and never echoed; no step
  prints env. Tauri imports the certificate into a temporary keychain.
- Signature verification before upload (D10); `SHA256SUMS` for manual checks.
- No job has cluster credentials or reads `~/.kube`; tests keep using fixtures,
  the fake API server (`crates/kubepit-core/tests/support`) and explicit paths.
- Distribution tokens are fine-grained PATs scoped to the tap repository
  (`contents: write`) and to the winget fork (public repo).

## Testing strategy

- `node --test "scripts/**/*.test.mjs"` (`pnpm test:scripts`) for every script,
  with temp directories that mimic Tauri's bundle tree and keys generated in
  memory at test time (never committed).
- Rust: the updater plugin's own `RemoteRelease` parser reads
  `scripts/release/fixtures/latest.valid.json`; the committed config merged with
  `fixtures/overlay.example.json` enables the updater.
- `actionlint` (with shellcheck) in CI and locally.
- `scripts/ci/test/workflows.test.mjs`: six checks present, OS matrix, SHA
  pinning, secret/variable names documented in RELEASING.md and vice versa.
- Dry run on a fork (`workflow_dispatch`, `dry_run: true`), then a real
  prerelease tag (`v0.1.1-rc.1` style, see open questions) before the first
  public release.

## Rollout

1. Land CI (`ci.yml`) and make `frontend`, `rust-fmt`, `rust (ubuntu-22.04)`,
   `rust (macos-14)` and `workflows` required in branch protection (user).
2. Land the release scripts and workflows; the user creates secrets/variables
   per RELEASING.md, the tap repository and the winget fork.
3. Dry run on a fork; then a prerelease tag; then the first public release.
4. The cross-platform plan flips the Windows job to required.

Pushing, branch protection, secrets and repository creation are user actions:
this worktree has no remote configured.

## Open questions

1. Windows signing provider: Azure Trusted Signing eligibility for an
   individual in Türkiye, SignPath Foundation, an OV cloud certificate, or
   unsigned for the first releases?
2. Is the Apple Developer Program membership in place (Developer ID +
   API key)? Without it the tap should wait (unnotarized apps need
   `--no-quarantine`).
3. First public version: `0.1.0` as committed, or `0.2.0`? Prerelease naming
   (`0.2.0-rc.1`)?
4. MSI for enterprise deployment, and arm64 builds for Windows/Linux — now or later?
5. Should `.deb`/`.rpm` installs update in-app (pkexec prompt) if the bundler
   signs them, or always defer to the package manager?
6. Tap name `erdembas/homebrew-tap` and winget id `ErdemBas.Kubepit` — OK?
