## Product boundary

Kubepit's existing local Kubernetes IDE remains genuinely open source and usable without an account, license server or subscription. The paid product adds **team profiles** and **AWS/GCP/Azure discovery and import convenience**, at **USD 3 per purchased user seat per month or USD 30 per purchased user seat per year**. The annual saving is `(36 - 30) / 36 = 16.666…%`, displayed as 16.67%; USD 2.50/month is an annual equivalent, not monthly billing. Existing manual kubeconfig import, cluster access, local cluster lifecycle and all other free functionality remain free. No cluster-count or resource-count paywall is introduced.

The commercial desktop implementation and this SaaS live in a proposed **private `kubepit-commercial` repository**. The public repository contains the free application and narrow documented integration contracts only. A public build must compile and pass its tests with no private checkout or private package registry. The private desktop build consumes a pinned public revision, retains its OSS notices, and adds proprietary code. Publishing this architecture does not require publishing proprietary implementation or secrets.

The user's current statement is that the code has not yet been pushed/distributed; do not assume an irrevocably released MIT baseline. The program proposes AGPL-3.0-only for the public core with an alternative commercial grant for the controlled core in the official combined proprietary build, a permissive integration SDK and proprietary premium/SaaS implementation. Copyright ownership, third-party compatibility and future contributor grants must be verified in the licensing workstream before distributing that combination. No license change or Git history reset is authorized by this planning document.

The cloud is a small account, collaboration and commerce service. It **does not proxy Kubernetes**, store kubeconfigs, host a cloud-provider credential broker, collect cluster logs or run customer commands. Paid cloud discovery/import executes locally in private Rust code using the user's existing CLIs and credentials. The service checks entitlement and stores explicitly shared, validated configuration metadata only. Server URLs, namespaces, notes and resource names can still be sensitive; the upload preview names what will leave the device.

## Goals and non-goals

- One account may belong to several organizations. Each organization has its own subscription, purchased seats, team groups and profile access rules.
- Owners can buy seats, invite people, assign access and cancel without contacting support. Billing administrators can administer billing without gaining profile data access.
- Signed entitlement leases let existing paid desktop workflows tolerate a short outage; the service always authorizes cloud access against current server state.
- Billing is resilient to retries, duplicate notifications, out-of-order events and ambiguous provider responses. It never grants access from a checkout redirect or client-supplied price.
- Configuration remains portable through explicit export; losing a subscription never deletes local credentials or blocks the OSS application.

V1 excludes enterprise SAML/SCIM, reseller billing, metered billing, usage-based AI charges, multiple subscription products per organization, multiple billing currencies, annual invoices paid by bank transfer, coupons, trials, custom domains, arbitrary external profile fetches, a public developer API, mobile apps and self-hosted commercial SaaS. These exclusions keep a USD 3 product operable. An adapter is not a promise to support every provider on launch day.

## Identity and sessions

### Web console

Use the hosted managed authorization-code flow through the official SDK. Register exact HTTPS callback URLs; validate single-use state, PKCE where supported and issuer/audience/nonce as required by the provider's selected protocol. Use its documented AuthKit API rather than assuming arbitrary generic OIDC endpoints. A provider's stable subject is identity; email is a verified contact attribute, not a primary key. Never link identities just because unverified email strings match. Recovery, password handling if enabled later and MFA are delegated to the provider; Kubepit stores no passwords or password reset tokens.

The backend completes authentication and creates an opaque browser session. The cookie is `__Host-kubepit_session`, `Secure`, `HttpOnly`, `SameSite=Lax`, path `/`, no Domain. Console/API use one origin; cookie-authenticated mutations require CSRF token plus Origin checks, exact CORS allowlists and JSON content type. Session idle expiry is 24 hours, absolute expiry 7 days; sensitive actions require managed reauthentication within 10 minutes. Provider session/refresh credentials, if needed, are encrypted server-side with separately managed keys and never placed in localStorage or returned to the browser. Application authorization always reads our memberships, not roles supplied in a browser or arbitrary IdP claims.

### Desktop browser approval

Use a narrow application login exchange, not a new password system or general OAuth server. WorkOS supports native PKCE flows; this design keeps managed login in the external browser and isolates desktop credentials from IdP refresh tokens. [Official native guidance](https://workos.com/docs/authkit/connect/oauth), [official example](https://github.com/workos/electron-authkit-example).

1. Rust creates a 32-byte random verifier, S256 challenge, random state and a P-256 device key. `POST /v1/desktop/login-attempts` records its proposed public-key thumbprint and returns a random attempt ID, 256-bit polling secret, server proof nonce and a fixed-origin browser URL. Only a hash of the polling secret is stored. Lifetime is 5 minutes; the key is not enrolled merely because its thumbprint was submitted.
2. Rust opens that URL in the system browser. The browser signs in through AuthKit. A review page shows the device name and a matching short verification code; an explicit, CSRF-protected approval binds the attempt to that authenticated user. Email links and GET requests cannot approve attempts.
3. Rust polls with the secret no faster than every 2 seconds. After approval it exchanges the attempt ID, polling secret, verifier and original state with a standard DPoP proof for the proposed device key and server nonce. In one transaction the server verifies S256, state and proof, consumes the attempt and creates a device session. A racing second exchange fails `LOGIN_ATTEMPT_CONSUMED`. No access token, refresh token or IdP token appears in a redirect URL, console logs or renderer state.
4. Return opaque application access and refresh credentials to Rust only. Access lasts 15 minutes. Refresh rotates on every use, expires after 30 days idle and 90 days absolute, and is hashed server-side. Refresh reuse revokes the family; concurrent legitimate refreshes are serialized in Rust rather than granting a broad replay grace. Store desktop refresh credentials and device private key only in the OS credential store. If the store is unavailable, offer a memory-only session with explicit sign-in after restart; do not write plaintext fallback files.
5. Rust owns HTTP calls; the renderer receives only account/organization names, session status and error codes. The device list and sign-out endpoints revoke sessions server-side; sign-out clears local credentials and signed leases. Up to 5 active desktop devices per identity by default; devices are not purchased seats and no invasive hardware fingerprint is collected.

Device proof uses standard [RFC 9449 DPoP](https://www.rfc-editor.org/rfc/rfc9449.html) and [RFC 7638 JWK thumbprints](https://www.rfc-editor.org/rfc/rfc7638.html), implemented with reviewed JOSE libraries. Require `typ=dpop+jwt`, ES256, public JWK, method/URL binding, short `iat` window, unique `jti`, server nonce and the applicable access-token hash. The API binds opaque access/refresh credentials to that thumbprint and requires matching proofs at refresh and protected desktop endpoints; verify using configured public URLs behind a trusted proxy, not attacker-supplied Host headers. Reject replayed proofs in a bounded shared replay store. This prevents a supplied fingerprint alone from enrolling a key. Rust's offline lease gate also checks possession of the matching local key; it must not accept an arbitrary claimed fingerprint. OS-store key storage is not claimed to be nonexportable on every platform, and a fully compromised device remains outside the offline guarantee.

Pin DPoP policy beside the commercial constants: proof age <=60 seconds, future skew <=5 seconds, nonce lifetime <=5 minutes and replay record TTL >=120 seconds. The shared PostgreSQL replay table keys `(jwk_thumbprint,jti)`; it is an explicit global auth table, not a tenant-policy exemption by accident. Desktop token responses declare `token_type: 'DPoP'`; protected endpoints reject ordinary bearer presentation for these sessions. Shared fixtures in `packages/contracts/fixtures/desktop-dpop/` include `{ request: { method, url, nonce, access_token_hash? }, public_jwk, proof_jwt, expected_jkt, expected_error }` and clearly labeled deterministic **test-only** key material. The fixtures cover nonce/method/URL/token-hash mismatch, replay, skew and a thumbprint without proof. `commercial-policy.ts` generates the corresponding Rust-readable policy fixture.

Provider logout/session-revocation notifications revoke mapped application sessions; also reconcile identity status on refresh at most every 15 minutes. Internal token revocation takes effect on the next cloud request because opaque tokens resolve through the session store. A removed organization member loses that organization's access immediately without losing unrelated organizations. An IdP outage never turns an invalid credential into a valid session; existing application sessions may continue to their expiry subject to local revocation checks.

## Organization model, authorization and seats

An **identity** is a person who signed in. An **organization** owns billing and shared data. A **team** is a group within one organization for targeting profiles. No global “paid user” boolean exists. The same person using paid features in two organizations consumes a seat in each, and joining five teams within one organization consumes one seat.

| Operation                                                        | owner                  | admin                  | member                 | billing_admin      |
| ---------------------------------------------------------------- | ---------------------- | ---------------------- | ---------------------- | ------------------ |
| Read/use an allowed profile or paid local feature                | requires assigned seat | requires assigned seat | requires assigned seat | no profile access  |
| Edit/publish profiles and manage team targets                    | yes, with seat         | yes, with seat         | read/use only          | no                 |
| Invite/remove ordinary members, manage teams and seat assignment | yes                    | yes                    | no                     | no                 |
| Change roles to owner/admin/billing_admin; transfer ownership    | owner only             | no                     | no                     | no                 |
| View checkout, invoices and change/cancel purchased seats        | yes                    | no                     | no                     | yes                |
| Delete organization, organization export, full audit             | owner only             | no                     | no                     | no                 |
| Read operational team/member audit                               | yes                    | yes                    | no                     | billing audit only |

Administrative ownership/billing alone does not consume a seat. An owner/admin needs an assigned seat when using premium features; `billing_admin` cannot be assigned one until its role changes. A seat is assigned to an active organization membership, not an email address or device. There must always be at least one active owner; protect concurrent demotions/removals by locking the organization row. There is no support impersonation in v1; support uses redacted diagnostics and audited break-glass operational access outside the customer API.

There is one current subscription record per organization and no automatically created personal subscription. Subscription quantity is purchased capacity, not the count of active users. In normal `ready` state, `assigned + reserved <= allocation_ceiling` must hold after every allocation transaction, where `allocation_ceiling = min(settled_purchased_capacity, pending_lower_capacity)` while a decrease is pending, otherwise settled purchased capacity. The service serializes seat operations with `SELECT ... FOR UPDATE` on the org's seat-account row and uses constraints to prevent duplicates. Exceptional externally imposed under-capacity uses the explicit conflict state below rather than inventing capacity or deleting arbitrary assignments.

- Create invitation: owner/admin selects role, teams and whether premium access is included. Premium invitations reserve one slot atomically before mail is queued. Duplicate pending invites for the same normalized verified email return the existing invitation rather than reserving again. Invitations expire after 7 days; cancel/expiry releases reservations in the same transaction. Non-premium admin/billing invites reserve none.
- Accept: authenticate and require a matching verified email, lock invitation and seat account, consume its one-use 256-bit token hash, create/reuse membership and convert reservation to assignment atomically. An existing member's acceptance cannot create a second assignment; release any redundant reservation. Reject expired, wrong-organization and already-revoked invitations. Team IDs come from the same organization by composite foreign keys.
- Remove membership/unassign seat: revoke cloud access and increment membership entitlement version immediately; free assignment immediately. Do **not** silently decrease purchased quantity or promise a refund. Billing UI states that seats remain available and offers an explicit “Change purchased seats” action to authorized billing roles.
- Reduce purchased quantity: explicit preview and confirmation, quantity at least assigned + reserved, no mid-period automatic refund, reduced capacity applies on confirmed provider update and lower recurring charge on next renewal. Before remote dispatch, lock the seat account, recheck occupancy and atomically persist a pending lower allocation ceiling tied to the billing operation. Concurrent invitations/assignments honor that lower ceiling while the HTTP call is in flight; do not hold the DB transaction across HTTP. On confirmed failure restore the prior ceiling; on ambiguous timeout retain it until reconciliation; on success promote it to settled capacity. The owner may free or cancel reservations first; no arbitrary automatic eviction. This conservative v1 policy avoids a fragile scheduler at renewal boundaries.
- Increase quantity: preview provider-calculated proration, confirm exact amount/currency/tax context, request immediate prorated billing, and grant only after authoritative confirmation of the paid change. Pending or failed payment cannot allocate additional seats. Annual/monthly switches require separate provider-supported preview and confirmation; do not infer taxes/proration with local arithmetic.

If an external provider/admin change, refund or restored historical state proves settled capacity below existing assigned + reserved count, reconciliation atomically enters **`capacity_conflict`** and records the truthful lower capacity plus the retained assignments/reservations. It does not pretend the normal-state inequality still holds. Block new allocations, premium invitation acceptance, new leases and all ordinary paid cloud profile reads/writes for that org with `CAPACITY_CONFLICT`; keep account/billing/member administration, removing assignments/canceling invites, owner export/deletion and all free local work available. Bump entitlement version so a validly authenticated online client learns the org-wide suspension. Already offline clients keep only their previously bounded leases; downloaded data cannot be erased. The owner resolves by an explicit settled seat purchase or deliberate removals/cancellations until occupancy fits; a locked reconciliation then returns to `ready` and permits new leases. No arbitrary auto-eviction or forged purchased capacity. Database triggers forbid allocation increases in conflict state, but permit the narrow billing reconciler to record an externally proven decrease **only together with** the conflict transition and audit evidence.

Every tenant table has non-null `org_id`, composite unique/primary keys needed by references, `created_at`, and appropriate `updated_at`. Mutable entities carry monotonically increasing `revision bigint`. API IDs are not authorization.

An example cross-tenant guard is `FOREIGN KEY (org_id, membership_id) REFERENCES memberships(org_id,id)`, not a single-column FK to `membership_id`. A membership removal changes status and deletes its allocation in one locked transaction. Database triggers guard allocation mutations/capacity and reject invalid direct SQL as well as application mistakes; lock order is organization → seat account → memberships/invitations → allocations. Add check constraints for nonnegative quantities, exactly one seat target and bounded role/status values. Concurrency tests run against PostgreSQL 17, not SQLite or mocked SQL.

All tenant tables use `ENABLE ROW LEVEL SECURITY` **and** `FORCE ROW LEVEL SECURITY`, with `USING` and `WITH CHECK` predicates using `current_setting('app.org_id', true)`. Missing/empty context denies access. `api_runtime` and `worker_runtime` are nonowner `NOBYPASSRLS` roles and cannot change schema/policies, impersonate the migration role or `SET ROLE` to elevated roles. The migration/owner credential is absent from deployed API/worker secrets. PostgreSQL owners and `BYPASSRLS` roles normally bypass policies, so merely enabling RLS is insufficient. [PostgreSQL RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)

The application verifies the session, derives actor identity, checks active membership through a narrow identity-scoped resolver, begins a transaction on **one checked-out `pg` client**, and calls parameterized `set_config('app.org_id', orgId, true)` and `set_config('app.actor_id', actorId, true)`. The last `true` makes settings transaction-local. Every Drizzle query in that operation receives that same transaction handle. Never use session-level `SET` or run a transaction's query through the pool singleton. Commit/rollback resets context before release. RLS is defense against missing scope predicates, not a substitute for safe SQL or protection against a fully compromised API credential.

Global authentication/intake tables have dedicated restricted roles and narrow services; they are not silently exempt tenant tables. The webhook intake role only inserts verified events. A security-definer mapping function with fixed `search_path`, revoked PUBLIC execution and no dynamic SQL resolves a provider subscription/customer to an org. It returns only the ID needed to enqueue work; the worker then starts an ordinary tenant transaction. Membership discovery exposes only the authenticated person's memberships. Test each privileged boundary and include all newly added tables in the schema-policy guard.

## Billing state, economics and reliability

### Prices and accounting

Server-owned SKU records contain currency `USD`, recurring unit `month`/`year`, unit amounts `300`/`3000` and immutable provider price IDs. API accepts SKU + seat quantity, never an arbitrary amount or provider price ID. No free trial or credit-card storage in v1. Checkout quantities are 1–100 self-serve seats; larger requests are support-reviewed without inventing a different public price. Taxes are computed by the provider and displayed at checkout; marketing labels prices “plus applicable taxes” until merchant/provider/legal review approves the final regional presentation. Tax-inclusive jurisdictions must receive compliant total-price presentation. A Merchant of Record handles its covered transaction tax duties; business accounting, income taxes, privacy and statutory customer rights are still operator responsibilities.

A sandbox/startup price preflight fetches configured Paddle prices/products and verifies environment, active status, product identity, USD currency, unit amount, recurring interval/count, quantity policy and approved tax mode. A mismatch disables checkout and alerts the operator; never silently bill a configured ID merely because it exists. Production preflight is read-only, and immutable SKU upgrades require a reviewed migration rather than overwriting an old price's meaning.

Illustrative fee math only, using Paddle's **published headline 5% + USD 0.50**, not a quote for the USD 3 SKU. Excludes taxes, FX, refunds, chargebacks, discounts, payout adjustments and infrastructure. One organization is billed once per period for its total quantity, not once per seat. Actual sub-USD-10 fees must replace these examples after approval. [Published fee and low-price caveat](https://www.paddle.com/pricing)

### Provider adapter and lifecycle

`BillingProvider` exposes `createCheckout`, `getCheckout`, `previewChange`, `applyChange`, `cancelAtPeriodEnd`, `resumeRenewal`, `createPortal`, `fetchSubscription`, `fetchTransaction`, `verifyWebhook(rawBytes,headers)` and `normalizeEvent`. Capability flags describe actual provider behavior. Fake and selected production adapters must pass the same contract suite. No live Stripe adapter is required if Paddle qualifies; do not ship an untested placeholder advertised as working.

Normalized states: `none`, `pending`, `active`, `past_due`, `paused`, `canceled`, `expired`, `suspended_dispute`. Cancellation at period end remains active through **paid-through**, not through a speculative renewal date. Past-due/paused states may preserve previously paid time but never advance it; new purchases/seat increases remain pending until settled. A fully refunded current term, confirmed chargeback or explicit administrative security revocation can shorten entitlement immediately; a partial refund does not blindly revoke every seat and must map to the relevant provider adjustment and support decision. Reversal/recovery requires a reconciled authoritative state, not the mere arrival of an “active” old event.

Derive paid-through and newly purchased capacity from a confirmed paid/completed transaction and its line items for the **correct subscription, org customer, SKU, quantity and covered billing period**, including provider-documented settled-credit semantics if used. An `active` subscription or updated item quantity alone is insufficient: providers may update quantity while immediate proration collection fails. A previously paid term keeps only its proven capacity; pending higher provider quantity does not unlock seats. A confirmed no-refund decrease may lower capacity using the already-paid term and the reconciled provider change, without fabricating a new payment. Store transaction-to-entitlement evidence so renewal, proration, refund and replay decisions are explainable.

Payment failure and recovery use provider dunning. Web console shows actual billing status and an authorized portal link; it never shows provider secrets. Removing a member does not alter an invoice. Cancellation and quantity changes have a confirmation with next charge, effective date, refund treatment and retained local access. Refund policy and dispute fees depend on the approved provider contract and applicable rights; operators record audited decisions, not a hardcoded “never refund” rule. A billing portal may offer actions outside our seat constraints: configure/restrict it to payment details, invoices and supported cancellation actions, routing quantity changes through our service. If the provider cannot enforce this, reconciliation uses the explicit `capacity_conflict` policy, with truthful quantities and no arbitrary member eviction.

For Paddle, updates must state the intended proration mode; provider proration is authoritative. Quantity changes and when a charge is collected are separate concepts. Do not assume “next billing period” means the item mutation itself is deferred. [Proration](https://developer.paddle.com/concepts/subscriptions/proration/)

### Idempotency, webhook intake and reconciliation

All purchase/change requests require `Idempotency-Key` (UUID). Store the canonical request hash and operation before contacting the provider. Same actor/org/route/key + same body returns the same operation; different body returns `409 IDEMPOTENCY_CONFLICT`. A durable outbox sends the operation. Use provider-native idempotency only where documented; do not invent an unsupported header. Attach our immutable operation ID as provider metadata when supported. If a timeout makes creation ambiguous, set `pending_reconciliation`, look up the known object/correlation and reconcile; never automatically create another checkout/subscription or charge just because the HTTP response was lost. A partial unique lock allows one open subscription-creation operation per org. A second confirmed subscription becomes an operations alert requiring resolution; it must not double capacity.

The provider route reads bounded **raw bytes** before any JSON parser, checks its documented signature and timestamp tolerance with the official SDK, and verifies expected environment. Paddle signs the exact raw body and supplies a timestamp in `Paddle-Signature`. [Signature verification](https://developer.paddle.com/webhooks/about/signature-verification/). Signature validation precedes persistence and parsing; no request-body logging. Persist the event with unique `(provider,environment,event_id)` and an outbox job in one transaction, then acknowledge quickly. Duplicate verified events return success. A database failure returns a retriable error; never acknowledge an event that was not durably accepted.

Delivery can be repeated and out of order; provider `occurred_at` is evidence, not the processing time. [Paddle delivery model](https://developer.paddle.com/webhooks/about/how-webhooks-work/). Worker processing locks the subscription, fetches current provider state for changes affecting access or money, validates known customer/subscription/price/currency bindings, then updates subscription, seat capacity, entitlement version and audit atomically. Use timestamps/versions and transaction IDs to reject stale regressions; ambiguous order or same-timestamp conflicting updates triggers reconciliation. `custom_data.org_id` alone is never trusted as a membership or tenant mapping.

Reconcile pending operations every minute, recently changed/past-due subscriptions every 15 minutes, active subscriptions at least daily, and before issuing a lease if billing verification is older than 6 hours. Network failure cannot extend paid-through or refresh the authoritative entitlement timestamp. Run jobs with `FOR UPDATE SKIP LOCKED`, short leases, heartbeat, bounded retry with exponential backoff/jitter, a 10-attempt dead-letter state and operator-visible replay. Jobs and side effects have unique dedupe keys; lease expiry means another worker may repeat work. Business effects must be idempotent even when the job executes twice. No worker holds a DB transaction open during a remote provider HTTP call; re-lock and compare revision before applying the response.

## Signed desktop entitlement contract

Feature IDs are `team_profiles` and `cloud_import`. The single canonical constants source is `packages/contracts/src/commercial-policy.ts`: those IDs, 300/3000 USD cents, 24-hour freshness, 7-day total lease cap, fixed issuer/audience policy and schema version. Generate the Rust-compatible JSON fixtures and DTO/schema outputs from it; do not separately hand-maintain those values in the API, console and desktop. Only the backend computes entitlement from active membership + assigned seat + eligible subscription + device/session state. A locally set paid flag, a Stripe/Paddle browser event, a JWT issued by the desktop, an arbitrary org ID or an IdP organization claim is never authority.

`POST /v1/orgs/{org_id}/entitlements` authenticates a desktop session, verifies current membership/seat and reconciles stale billing, then returns a compact ES256-signed JWS:

```json
{
  "iss": "https://api.<approved-domain>",
  "aud": "kubepit-desktop-pro",
  "sub": "identity_uuid",
  "org_id": "organization_uuid",
  "membership_id": "membership_uuid",
  "device_key_thumbprint": "base64url-sha256",
  "features": ["team_profiles", "cloud_import"],
  "entitlement_version": 4,
  "jti": "lease_uuid",
  "iat": 1790000000,
  "nbf": 1790000000,
  "authoritative_at": 1790000000,
  "fresh_until": 1790086400,
  "grace_until": 1790604800,
  "paid_through": 1792000000,
  "exp": 1790604800
}
```

The times above illustrate a shape only. Production values satisfy:

```text
fresh_until = min(authoritative_at + 24 hours, paid_through)
grace_until = min(authoritative_at + 7 days, paid_through)
exp = grace_until
```

Seven days is the total window from the last authoritative validation, **not** seven days after the first 24 hours, and never beyond the paid term. `authoritative_at` is server time after current membership/seat checks and a sufficiently recent authoritative billing validation; a failed refresh, a restarted client or a local clock adjustment cannot reset it. Rust verifies fixed issuer, audience, ES256 algorithm, allowlisted `kid`, signature, subject/org/device, all time ordering and current cached entitlement version. Keys are public verification material shipped in the paid app; private signing keys live in a managed KMS/HSM supporting P-256, not environment text or the repository. Key rotation overlaps verification keys for maximum lease + deployment skew; emergency compromised-key response may require an online refresh/new application build because offline clients cannot learn revocations instantly.

Refresh on sign-in, organization switch, foreground when stale and approximately every 12 hours with jitter. Fresh valid leases enable paid **local** operations; after 24 hours transport failure may use the remaining grace with a translated notice. `ACCESS_TOKEN_EXPIRED` first triggers one serialized refresh and request retry; it does not revoke an org's lease. A profile's ordinary `FORBIDDEN_ROLE`/404 affects that resource only. Only an authenticated authoritative entitlement/membership/seat denial (`MEMBERSHIP_REVOKED`, `SEAT_REQUIRED`, `SUBSCRIPTION_REQUIRED`, `ENTITLEMENT_REVOKED`, `CAPACITY_CONFLICT`) invalidates the affected org lease; confirmed `SESSION_REVOKED`, refresh-family revocation or logout invalidates the affected session's leases. These known denials cannot use outage grace. A refresh transport failure may use an already valid local lease without extending it. Unknown key, tampered token, invalid claims or clock rollback require online validation. Track maximum trusted server time plus monotonic elapsed time during a run and persist a high-water mark; recognize that a fully controlled offline device cannot offer perfect rollback resistance or instant revocation. Do not make stronger DRM claims.

Known revocation is immediate; an offline device that has not learned of removal can retain previously leased local premium access until its signed cap (at most 7 days from its last authoritative validation, or earlier paid-through). Downloaded profile data cannot be remotely erased. Both limitations must appear in customer/security documentation rather than being hidden behind a promise of instant offline deprovisioning.

Cloud profile reads/writes never accept a cached lease in place of live session, membership, role and seat checks. The service's paid API requires current authorization even while a local lease is in grace. An owner without a seat can still manage billing/members and export/delete the organization's data. After expiration, sign-in, billing, data export, profile unlink/removal and free local work remain available. Stop new automatic premium sync/discovery; keep already imported clusters as ordinary local clusters and keep the last applied configuration readable. Downgrade never silently removes local clusters, credentials or safety restrictions. Existing operations complete safely or cancel without partial credential replacement; the desktop plan defines those transaction boundaries.

## Team profile storage and sync

Use the commercial desktop's versioned, credential-free document schema: **`kind: KubepitTeamProfile`, `version: 1`**, with a stable slug `document.id`. The REST envelope has its own UUID `id`, server-owned `org_id`, integer `revision`, `document` and `targets: { scope: 'organization' } | { scope: 'teams', team_ids: UUID[] }`; document contents cannot assert organization authority. Preserve the existing planned YAML `version` field rather than renaming it `schema_version`; API schema versioning remains separate. Publish interoperable schema contracts without publishing implementation. Shared content includes cluster metadata/settings, views, bookmarks, actions, health ignores and alert rules selected in the upload preview. Explicitly exclude kubeconfig text, tokens, passwords, certificates, exec-auth definitions, credentials in URLs, provider environments, local file paths, history/logs and arbitrary blobs. Nested credential-shaped keys fail validation; bounded secret-pattern scans flag suspicious free text and block known secret patterns pending local correction. A validator cannot prove all free text is nonsensitive: UI must present the exact payload for review and support omission/redaction.

Each profile has immutable revisions, a document SHA-256 and an ETag `"p:<uuid>:r:<integer>"`. Writes require `If-Match`; initial creation uses `If-None-Match: *` or idempotent POST. Missing precondition returns 428, stale revision returns 412 with current metadata but no unauthorized document. Reject unknown schema versions, unresolved references, cross-org targets and oversized/deep input. Initial limits: 1 MiB/document, 50 profiles/org, 100 revisions/profile or 90 days (whichever retains fewer, always keep head), 500 clusters, 2,000 views, 2,000 bookmarks and 500 actions per document; org aggregate live storage cap 100 MiB. These are protection limits, not additional paid tiers.

Visibility is org-wide or a set of teams. Owners/admins see/manage all profiles; seated members see only allowed profiles. Removing a team membership immediately removes cloud access; cached data cannot be remotely erased from an offline device. The desktop reconciles on next connection, removes the subscription layer while preserving ordinary local cluster connections, and explains the change. Never describe read-only team hints as an enforceable Kubernetes security boundary.

V1 sync is explicit pull and foreground polling with ETag (60 seconds ± jitter while the paid team screen/subscription is active, pause offline/background). `GET /profiles` includes accessible metadata and revisions; `GET /profiles/{id}` supports `If-None-Match`/304. No WebSockets, database replication or server-to-desktop commands. When edits conflict, preserve the draft, fetch the latest authorized version and offer review/retry; no last-write-wins merge. Deletion leaves a tombstone for 30 days; later list reconciliation also removes missing IDs, so long-offline clients do not depend on indefinite tombstones. Downloaded custom actions still require local explicit trust per content hash and never execute because a remote profile changed.

## Privacy, audit, deletion and operations

Secrets are never logged. Pino redaction removes authorization/cookie/signature headers, tokens, verifiers, invitation links, provider keys and bodies of profile/auth/webhook routes. Audit records action, actor, organization, target ID, outcome and changed **field names**, not cluster secrets, profile bodies or payment details. Restrict IP/user-agent collection to necessary abuse/security records; hash/truncate where appropriate and document it. Default operational logs 14 days, security logs 30 days, tenant audit 90 days, raw encrypted webhook payload 7 days, event IDs/processing metadata 400 days to prevent replay. Financial document retention follows the merchant/provider/legal decision, isolated from product data; never promise blanket deletion of legally retained records. These durations are proposed defaults for approval, not claims about law.

Owner export includes memberships/teams, owned profile revisions within retention, settings, audit and billing references in JSON/YAML; personal export includes only that person's data. Exclude credentials, provider payloads and other tenants. Build export with a tenant-scoped worker, encrypted temporary object, 15-minute authenticated download link and 24-hour object deletion; audit access. Export/download works after paid expiry. Profile direct export remains available for authorized members' accessible data during active membership; departing users cannot export another organization's data after removal.

Organization deletion requires recent managed reauth, typed organization name and explicit handling of subscription cancellation. First freeze premium writes and block new checkout, enqueue idempotent cancellation and show its result; do not report successful deletion while an untracked renewing subscription remains. Apply a 7-day undo window, then delete product data and revoke devices' org leases; backup copies age out within the approved retention. Retain minimal legally required financial records under a documented restricted purpose. Identity deletion requires transferring sole ownership, removes memberships and sessions without canceling other organizations' subscriptions, and requests managed-provider deletion. Account recovery and legal holds have audited, documented operator procedures.

Deploy one API instance and one worker process initially, with managed PostgreSQL in the same region, managed TLS, KMS/secrets manager, object storage only for short-lived exports/backups, and a transactional email provider for invitations/security messages. Email templates are fixed EN/TR with no arbitrary user HTML. Use verified sending domains, bounce/complaint handling and invitation resend limits; abuse cannot turn invitations into an unlimited email relay. Static console assets use local fonts and a restrictive CSP. Configure egress only for selected auth/billing/mail services and observability; no arbitrary profile URLs or customer Kubernetes servers.

Provisional first-release targets: monthly infrastructure spend **<= USD 60 before payment fees**, alert at USD 40/50/60, no silent autoscaling above approved cap; p95 ordinary metadata API <500 ms at 50 concurrent users, webhook intake <2 s, pending billing operation alert after 10 minutes, successful job backlog oldest <5 minutes. These are engineering budgets, not hosting quotes or contractual SLAs. Start with pool cap 10/API + 5/worker, bounded concurrency 4 external calls/worker, request timeouts, per-identity/org/IP rate limits, maximum 100 seats/50 teams/500 pending invites per org and 1 MiB profile body. Tune with measured fixture loads before offering more.

Managed PostgreSQL must provide encrypted backups and PITR; provisional **RPO <=15 minutes, RTO <=4 hours**, 7-day PITR plus encrypted daily snapshots retained 30 days. Test a restore into an isolated environment quarterly and before launch; verify tenant counts, policies, migrations and billing reconciliation after restoration. Keep app deploy and migration runbooks: expand/contract migrations, preflight backup, no destructive downgrade rollback, previous compatible image for application rollback, deferred cleanup after confidence. Restoring a database can resurrect old token state or forget processed webhooks: restore procedure rotates/revokes application session families, invalidates pre-restore lease versions on next connection, then reconciles provider state before serving premium writes. Never restore an old database and start billing blindly.

Monitor authentication failures, cross-tenant denies, signup/invite abuse, seat conflicts, webhook age/signature failures, provider mismatches, reconciliation drift, charge ambiguity, job retries/dead letters, entitlement issuance/rejections, storage growth and spend. Alerts contain IDs and codes, no raw secrets. No public admin panel or unrestricted impersonation. Operational repair tools require restricted operator credentials, explicit org ID, dry-run preview, ticket/reason and append-only audit. Document key rotation, IdP outage, billing outage, database restore and tenant-data incident runbooks.

## Verification and acceptance

Use deterministic fake identity/billing/email/clock adapters and ephemeral PostgreSQL 17. No tests use real clusters, `~/.kube`, production provider accounts, customer email or real cards. Manual sandbox tests require test accounts and published test payment methods, separate from fixture CI. A localhost test database is not production; default scripts require `KUBEPIT_TEST_DATABASE_URL` with an allowlisted local host and `kubepit_test_` database name and refuse generic `DATABASE_URL` fallback.

Critical proofs: cross-org guessed IDs and composite FK violations fail; pooled contexts cannot leak; runtime roles cannot bypass RLS; two concurrent last-seat invitations allocate exactly one; acceptance and expiry race safely; sole-owner concurrent removals fail; duplicate/late/missing provider events converge; ambiguous payment timeout never double-charges; removing a member frees a seat without modifying billing; provider failure cannot extend paid-through; browser redirects cannot grant entitlement; ES256 tamper/wrong-org/wrong-device/clock rollback/expired grace fail; expired license leaves all OSS workflows usable; explicit revocation defeats outage fallback; same profile edit race preserves both drafts; secret fixtures never appear in cloud uploads, logs, exports or audit. An end-to-end sandbox rehearsal covers purchase → invite → profile sync → seat removal → cancel → export → delete.

The execution plan defines 26 bounded tasks, exact target files and required test commands. All implementation remains future work until the handoff agent executes those tasks. Provider onboarding, prices, signing keys, deployment credentials, legal approvals and publishing are separate launch gates; a checkbox cannot be checked merely because a fixture passes.
